# ══ §Sampling: what to feed the checker ══
SA1  | route=method     | ref=§Sampling | Sampling is the precondition, and it is harder than building the checker. | src=report.md §Sampling
SA2  | route=method     | ref=§Sampling | Random inputs don't work: if a bug needs three unusual conditions each showing up one input in ten, a random input hits all three one time in a thousand; four conditions, one in ten thousand. | src=report.md §Sampling; numbers 1-in-10, 1-in-1,000, 1-in-10,000
SA3  | route=citation   | ref=§Sampling | The standard answer is combinatorial testing: build the input set so every pair or triple of conditions appears together at least once — affordable because most software failures are triggered by two or three conditions (Kuhn, Wallace and Gallo, IEEE TSE 30(6), 2004). | src=report.md §Sampling; truth-maker: Kuhn/Wallace/Gallo IEEE TSE 30(6) 2004 (not held)
SA4  | route=result     | ref=§Sampling | Real inputs are cheaper still: they are made by a small number of producers, each making the same choices every time, so a few hundred real files cover the combinations that actually occur — this is why the PDF corpus worked. | src=report.md §Sampling; number "a few hundred"; grounded in software-correctness.md (few PDF generators share behaviours; a handful of patterns)
SA5  | route=method     | ref=§Sampling | Producers cluster by time, customer and application, giving a coverage count: which producer × application × version cells we hold, and which shipped cells are empty. | src=report.md §Sampling; producer clustering corroborated by software-correctness.md
SA6  | route=method     | ref=§Sampling | Customers cluster too, so a pattern that is 0.1% of global traffic can be 100% of one customer's; sample evenly across cells, never in proportion to volume. | src=report.md §Sampling; numbers 0.1% / 100%
SA7  | route=method     | ref=§Sampling | New driver versions open new cells so the corpus goes stale; watch the fraction of newly seen inputs that match no held cell. | src=report.md §Sampling
SA8  | route=method     | ref=§Sampling | Independent implementations (poppler, mupdf) are weakest on common files and strongest on our tail — enterprise MFP drivers, line-of-business applications, old versions at regulated customers. | src=report.md §Sampling
SA9  | route=method     | ref=§Sampling | Everything above assumes the producer doesn't care about us; an attacker changes inputs based on our responses, can read our product, and creates inputs no driver would — so random sampling is back to hopeless. | src=report.md §Sampling; the attacker case grounded in vuln-finder-hive.md (attacker holds shipped code; cost-to-find dominates)
SA10 | route=method     | ref=§Sampling | The case is decided by who makes the input, not which product the code is in: a redaction feature in a document product parses attacker-chosen input and belongs to the security case. | src=report.md §Sampling; "who makes the input decides the case" grounded in vuln-finder-hive.md (the instance travels, the reason for it doesn't; threat-model move)

SE2  | route=method     | ref=§Security | The loop is a deterministic exploit check plus adversarial simulation: point an LLM at the shipped product with no internal knowledge; anything it finds that our own review missed is a measured gap. | src=report.md §Security; grounded in vuln-finder-hive.md line B (blinded simulation) + line A (enumerate attack surface)
SE3  | route=method     | ref=§Security | Three non-negotiables: the blind (if it sees our findings/history/notes it is simulating us, not an attacker, and the result is void); a deterministic check (looking at the response not the path certifies attacks that never happened); several runs and a known positive (one run is one sample; finding nothing means nothing until the instrument has found something). | src=report.md §Security; grounded in vuln-finder-hive.md (line B blind; positives are the measured gap, negatives weak; baseline needs pinned model set)
SE4  | route=prediction | ref=§Security | Use more than one model family and a human red team, because our model's blind spots are the attacker's model's blind spots but not a human attacker's [decays]. | src=report.md §Security; corroborated by vuln-finder-hive.md (model set/versions must be pinned in the manifest; blind held across a cloud org is open)
SE5  | route=method     | ref=§Security | Re-run every model release against the frozen exploit checks and count what the new model finds that they miss — that count is the rate at which our security tests go stale; a test with no such measurement since the last release should be treated as unreviewed. | src=report.md §Security; corroborated by vuln-finder-hive.md (a prior AI review is a baseline only if model versions were pinned at the time)
SE6  | route=data-gap   | ref=§Security | None of this gives a coverage figure until we have listed every externally reachable entry point — that list is the denominator, and it is a day's work that has not been done. | src=report.md §Security; grounded in vuln-finder-hive.md line A (the only line that yields a coverage denominator, goes first); restates NS5

# ══ §What to avoid ══
AV1  | route=method     | ref=§What to avoid | Avoid anything that still needs a human per change: better code generators (acceptance, not generation, is the bottleneck), better review prompts, specifications without tests, tests without refuters, checkers that share code with what they check, trusting a model version as if it were a compiler, counting lines or defects per KLOC. | src=report.md §What to avoid; restates OV13
AV2  | route=method     | ref=§What to avoid | Avoid anything that samples the wrong inputs: random inputs, corpora weighted by traffic volume, filing code by product instead of by who produces its input, and using the PDF result as evidence about WPP or security. | src=report.md §What to avoid

# ══ §Tests are code too ══
TC1  | route=method     | ref=§Tests are code too | A checker must not share code with what it checks; where it does it cannot see bugs in the shared code and a second check sharing nothing is needed — learned in the redaction work (two independent readers must agree) and in the codec (a shared toInt32 hid a bug for 10,000 checks). | src=report.md §Tests are code too; restates WP6; truth-maker: redaction + codec records (not held)
TC2  | route=method     | ref=§Tests are code too | A checker watches one channel and says nothing about the others; every checker states what it observes, and a partition is covered only when every channel a bug could live on has a checker. | src=report.md §Tests are code too
TC3  | route=result     | ref=§Tests are code too | Text gone from a PDF's content stream can still be in its metadata; bytes can be clean while the rendered page is not. | src=report.md §Tests are code too; truth-maker: redaction record (not held)
TC5  | route=result     | ref=§Tests are code too | Our 65/65 WPP result is the same shape — right answer, wrong channel. | src=report.md §Tests are code too; restates WP-65; truth-maker: WPP 65/65 record (not held)
TC6  | route=method     | ref=§Tests are code too | A refuter checks behaviour not design: a fix can pass its refuter and still be the wrong shape, and that judgement stays with a person. | src=report.md §Tests are code too; restates WP7
TC7  | route=method     | ref=§Tests are code too | Frozen is not forever: tests against a driver population go stale as drivers update (trigger: the corpus staleness figure); tests against an attacker go stale as models improve (trigger: a model release). | src=report.md §Tests are code too; restates SE5, SA7
